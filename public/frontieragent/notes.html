I

写报告的原理

分析一下这个项目：它写报告的原理是什么，为什么写出来的报告会好？

报告正文是子智能体报告的逐字合并，最后一步只加引用。质量来自拆题、取证、印证、验证，而不是文笔。

II

用什么模型，出了问题怎么兜底

它用的是什么模型？怎么做兜底：比如模型幻觉出了错误的数字、重复输出同一个字直到撞上输出长度上限（maxToken）、输出的 JSON（一种结构化数据格式）不合规，这些问题怎么处理？

不绑定模型，官方搭配 Apodex-1.1。重复、截断、格式、接口都有分层兜底；数字正确性没有代码校验，只靠流程与复核。

III

编排模型如何被约束

它的核心是编排模型。如果编排模型输出质量差或出现幻觉，整个任务岂不是会被拉低、越走越远？它是怎么控制编排阶段的模型，怎么约束和安排它分发任务的？

不给它获取事实的工具，派发要过五道代码处理，运行中有观察器纠偏，结束前由独立审查者重列子问题。

IV

长链任务为什么不崩

一个写报告的长任务有很多小环节，任何一个出错都可能导致失败或质量下降。100 个节点、每个 90% 的稳定性，乘下来整体就非常低了，这个项目是怎么解决的？

不追求每步 100%：让失败能被发现并换条件重试，出错降级不中断，并联代替串联，用闭环阻止错误传播。

§ 01写报告的原理

项目全景：一个协调者，一群子智能体

FrontierAgent 是 Apodex 团队开源的智能体运行时、终端产品和评测套件，面向长时程的研究型、文件型任务。它有两条内置工作流：单个智能体独立工作的 Stateful ReAct（有状态的“推理—行动”循环），和本笔记的主角——智能体团队（Agent Team）。智能体团队的报告不是“写”出来的，而是一条链路层层产出的：拆题、并行研究、逐字合并、独立复核、最后只加引用。

组成负责什么
Stateful ReAct一个有状态的智能体独自完成调研、读文件、写交付物、跑命令，在任务级沙箱里迭代
智能体团队协调者维护任务看板，把独立的工作派给并行的子智能体，收集结构化报告，再合成最终结果
frontier_agent/通用的智能体循环、调度、注册表、智能体之间的消息总线（AgentBus）、观察器（在每一轮前后插入检查的逻辑）
plugins/tools/网页、命令行（shell）、文件、沙箱、团队协作等工具的实现与安全策略
workflows/ReAct 与智能体团队的流水线、配置档（profile）、提示词、观察器
apodex/命令行与终端界面、操作审批、会话存档、运行轨迹记录（trace）、Docker 运行方式
benchmarks/评测框架，只作为消费者，框架代码从不反向引用它

两条流水线，一个开关

智能体团队注册了两条流水线：基础版（agent_team）在协调者产出答案后直接结束；报告版（agent_team_report）在协调者之后多接一个报告员节点，走不走这一步由一个条件判断函数决定。项目自带三个配置档，定位各不相同：

任务沙箱

命令行和文件工具共享一个按任务隔离的文件系统：输入目录（/inputs）只读，放用户给的材料；工作目录（/workspace）放研究和验证过程中产生的候选文件；输出目录（/outputs）放最终交付物。沙箱建立失败或命令鉴权失败时一律中止，绝不退回到无隔离的宿主机上执行。

§ 02写报告的原理

反直觉的一点：它没有“写手”

读完代码最大的发现是：整条链路里没有一个自由发挥的“写报告的大模型”。报告正文是协调者把子智能体报告逐字合并出来的；最后的报告员在提示词第一句就被定义成“引用挂载器”，只准往正文里插入 [N] 形式的引用编号，正文一个字都不许改。

译文你是引用挂载器，不是编辑，也不是写手。……你唯一的工作是往草稿里加 [N] 标记，其余部分原样返回。You are a citation attacher, NOT an editor or a writer. … Your ONLY job is to add [N] markers to the draft and return it otherwise unchanged.译自源码提示词 · workflows/agent_team/prompts_report_fast.py

为什么要把最后一步限制得这么死？提示词里直接写了原因：早期版本曾经让报告员做改写，要求它压缩篇幅、删掉空话、把过于精确的数字改成区间、调整“全部/绝不”这类量词，结果每一条都让报告丢掉了一半以上的数值内容。于是这些要求全部被列进了“明确不是你的工作”：

  • 篇幅、结构、章节顺序：即使草稿看起来太长、太短或有水分，也不动。
  • 风格、语气、套话：模糊的强调词、氛围铺垫、收尾的修辞原样保留。
  • 过于精确的数字：没有引用来源的“17.3%”就保持“17.3%”，不改成区间或数量级，也不删；不加引用就是完整、正确的处理。
  • 量词范围（“全部”“绝不”之类）：不增加也不去掉限定。

这一节的结论

报告质量几乎完全在“上游”决定：拆题决定完整性，子智能体的检索与计算决定正确性，逐字合并决定细节是否保留，复核决定错误能否被拦下。最后一步的任务被刻意缩到最窄，因为越窄越不容易做错，也越容易检查。

§ 03写报告的原理

先想后拆：把计划写到看板上

协调者的提示词第一步是“先想，不要先派活”：只把问题想到能拆的程度，不去求解，更不能一上来就派搜索智能体。想清楚之后，把每个具体、可检查的子问题登记到任务看板上。计划从此不再只存在于模型的脑子里，而是一份代码能读、能检查的结构。

第 1 步理解，然后拆解

  • 只推理到“能规划”为止：真正问的是什么、问题的结构和形状、真实的子问题、正确解应当是什么样子。求解、推导、计算、检索都是子智能体的事。
  • 不要用派子智能体（尤其是搜索智能体）开场：搜索和计算是团队在执行一个已经想好的计划，不是第一步。在不带规划的终端配置里，协调者甚至拿不到网页搜索工具，逼它先推理再派活。
  • 涉及文件产出时，先从用户原话里定出最小交付清单：文件数量、格式、在输出目录下的绝对路径。用户要一张图，就不要扩成 PNG + SVG；要一个设计稿，就不要附带 README / CSV / JSON / XLSX / HTML。研究和验证的中间文件只是工作目录里的候选，不是交付物。
  • 用“添加任务”工具（add_task）把理解落到看板：每个任务是一个具体、可检查的子问题或工作单元；建团队之前先自查计划是否完整、形状是否合理。
  • 多跳问题里，每一跳的中间实体都单独成为一个任务。
  • 按题型拆：推理 / 数学 / 逻辑题拆成“求解任务”，由子智能体推导并证明（写 Python 程序在命令行里暴力验证小规模情形、检验猜想），而不是“去网上搜答案”；事实 / 研究题拆成“检索 + 独立交叉印证”。

第 2 步建团队、派任务

  • 计划看起来合理后，才给每个任务配智能体。一个任务可以派给多个智能体，用来提速或交叉验证。
  • 一个角色一个专家，而不是一个查询一个智能体。角色是一类工作（搜索、推理、验证），同一个专家会多次收到派活（派任务工具 assign_task），并记得之前做过的事。
  • 智能体的名字写角色（lit_search、match_researcher、fact_checker、final_verifier），不写具体查询（italy_austria_check），否则无法复用。
  • 创建时的系统提示词只描述这个智能体“是什么”（角色和技能），具体任务在每次派活时再写。

第 3 步看报告、补缺口

  • 拿每份报告对照第 1 步的子问题清单逐条检查。
  • 报告缺具体数值、公式或关键细节 → 给同一个智能体派追问，它记得之前的工作，不必重新研究。
  • 需要核实、收窄或交叉检查报告里找出的候选（例如“找到的 6 场比赛逐场查详细数据”）→ 也派给同一个智能体，不要每个候选新建一个智能体。
  • 某个子问题完全没有报告 → 新建智能体。

看板规则

  • 只有子问题已回答且被印证（≥2 份独立报告，或经过验证）时，任务才能标为“已解决”；子智能体跑完了不等于解决了。
  • 真正走不通的任务标为“受阻”，原因写进备注。
  • 一个任务可以有多个负责人，多人同攻一题正是交叉印证在看板上的体现。
  • 看板实时显示每个负责人的执行状态，例如“web_a 运行中 · web_b 已交报告”；协调者只填结论、负责人和备注，执行状态由系统从消息总线读取。
  • 结束受看板约束：只要还有“待办”或“进行中”的任务，协调者提交的纯文本答案不会结束运行，会被要求先把任务解决或取消。

§ 04写报告的原理

子智能体：用统一格式交报告

每个子智能体只拿到一个聚焦的子任务，独立、精确地解决它，最后调用“提交报告”工具交一份固定格式的报告，调用后循环立即结束。这份格式是整条链路的“接口协议”：协调者靠它逐字合并，证据观察器靠它抽取来源，最高强度模式靠它决定下一轮往哪里投入。

七个字段的具体要求

字段要求
范围（Scope）被要求做什么，以及怎么做的：推理、检索，还是两者都有
发现（Findings）覆盖每一个方面。每个已解决的点都要写出精确原子：数字、单位、日期、名称、公式。绝不四舍五入、绝不改写，因为协调者会逐字复制，丢一位数或改一个名字就是丢分。每个点标明是“推导得出”（推理、证明或计算）还是“检索得到”（来源中写明），并说明如何验证
证据（Evidence）每条支撑一行：来源（网址逐字复制 + 原文数据，例如“论文写明 X = 47.3%”，并标质量：高 = 一手、官方或同行评审，中 = 一般网站或新闻，低 = 论坛或未经证实）；计算（代码 + 关键输出，如“用 sympy 数学库算出 Z = 3.14159”）；推导（证明或不变量 + 验证它的小规模检查，如“n = 1..8 暴力验证成立”）
置信度（Confidence）高 / 中 / 低，并用“验证得多充分”来解释
未解决（Unresolved）所有没能确认的内容，不许藏起来；只有真的什么都没剩时才写“无”
反面证据（Disconfirming）反对自己结论的证据或反例，以及什么会证明它错；没有就写“未发现”
冲突（Conflicts）来源之间或推导之间的矛盾，没有就写“无”

取数的纪律

  • 读网页只用网页读取工具（web_fetch），不在命令行里用 curl、wget 这类下载工具或 Python 网络库。网页读取工具能执行页面里的 JavaScript、绕过大部分反爬措施，并按要求直接抽取所需内容；就网页文字而言，命令行被当作“没有网络”。
  • 网页读取效果不好时也不要退回命令行下载（那样不执行 JavaScript、不处理反爬，还得自己解析原始网页代码）。正确做法是：把“要抽取什么”说得更窄再试；换一个载有同一事实的网址（移动版、AMP 精简版、打印版、缓存页、底层数据接口、聚合站）；或者回到网页搜索，找一个真正提供内容的来源。自己拼出来的网址只能用来“读”，不能拿来引用，只有实际返回了内容的那个网址才能写进“证据”。
  • 网址必须从工具输出里逐字复制：不去掉问号后面的参数（如 ?query=），不因为旁边的链接有 .html 就补上，不互换 m. / amp. / www.，不“补全”看起来被截断的网址。网站对改错的网址常常返回“成功”状态码（HTTP 200）加一个错误页面，工具不会报错，它只会悄悄变成报告里的死链。网址看起来不对时，就实际读一次，引用确实能返回内容的那种写法。
  • 两个例外，判断标准是网址实际返回的是什么：① 二进制文档（.pdf .xlsx .docx .pptx .zip），需要翻页或逐格读取时，可以用命令行把文件下载到本地再处理，因为网页读取工具没法直接跳到 300 页 PDF 的第 217 页；② 原始数据端点（.json .csv .xml、/api/、api.php、wp-json、output=json），并且需要精确计数、全部记录或跨行计算时，下载后用 Python 等工具处理。源码注释里记了一次实测：网页读取工具处理一个含 100 条记录的 JSON 文件，只报回了 60 条。
  • HTML 页面永远不属于例外，不管它多像表格、需要多少条。把网页存到本地再用文本搜索或正则表达式提取，正是这条规则要禁止的做法；要很多条，就让网页读取工具一次抽出（比如“所有公告标题及其网址”）。本地的输入文件用读文件工具，不用网页读取工具。

证据卡从哪里来

子智能体身上挂着一个证据观察器（EvidenceObserver），它被动地从网页搜索、网页读取、命令行、写文件这几类工具的结果里抽取“证据卡”，并按域名给权威度加分，例如 .gov +0.12、.edu +0.10、nature.com 与 science.org +0.10、arxiv / pubmed / ieee / acm +0.08、reuters +0.07、wikipedia +0.04。另一个断言观察器在循环结束时把同一查询下的证据卡归并成“断言”，不需要额外的大模型调用。这些卡片随报告一起汇总到协调者，最后成为报告员的候选来源。

按领域追加的指引（可选）

“领域指引”开关（include_domain_guide）打开时（科学类评测使用），研究型子智能体会额外拿到领域指引：物理题一律用 Python 数学库（sympy、scipy）推导并做数值验证；化学计算题全程用 Python 分步求解，机理题写全催化循环的每个中间体和氧化态；生物题去 PubMed / PMC 找一手论文，写出准确的基因符号、浓度和时间点。

§ 05写报告的原理

逐字合并：让细节不在汇总时丢失

多智能体系统最常见的问题是：每一层总结都会丢细节、磨平数字，最后报告又空又泛。FrontierAgent 用第 4 步的“逐字合并”专门对付它：协调者到这一步才开始“为了回答而推理”，但写法被严格限定为复制和取舍，而不是重写。

第 4 步七条规则

  1. 逐字复制：从解决了该子问题的报告里，复制最具体的内容，不改写、不总结、不压缩。
  2. 保留原子：每个数字、单位、日期、公式、引用和专有名词都必须与报告中完全一致，不取整、不归一化、不翻译、不改写。
  3. 补缺口：某份报告漏了某个子问题，就从覆盖它的报告里原样取来。
  4. 按证据强度仲裁冲突：看有几个子智能体印证、来源质量如何、证据是否直接，选支撑最强的答案，绝不取平均，也不折中。
  5. 长度偏好：草稿至少要和最详细的那份报告一样详细，聚合细节而不是缩减。例外：如果任务规定了答案格式（例如只要一个值），格式要求优先，哪怕答案因此很短。
  6. 不编造：不引入任何报告里都没有的事实。
  7. 标注来源：在每个关键的检索事实后加 [1]、[2]，文末列出参考文献，每行一个“[1] 网址”，网址从子智能体报告的“证据”栏逐字复制，包括问号后面的参数，绝不“整理”（不补 .html、不换 m. / www. 前缀），因为改过的网址无法再核对，往往返回错误页而不是报错。同一来源复用同一编号；推导或计算出的结果不需要网址，注明推导过程或审查员即可。答案格式有规定时同样以格式为准，不附参考文献。

多跳问题还要求在最终答案之前，先写出已经验证过的中间实体链条。

第 5–6 步验证、修订、提交

  • 第 5 步：创建终审员，把原始问题和完整草稿全文放进任务提示里交给它（详见下一节）。
  • 第 6 步：修复审查员找出的问题，确保每个子问题都有答案。如果缺口是实质性的（子问题仍未回答、审查员发现真实错误、证据太薄），可以回到第 1 步重新拆题、追加任务、再派一轮，而不是交一份弱答案。
  • 修订时继续遵守逐字合并的纪律，保留正文里的 [n] 和文末参考文献（答案格式另有规定时除外）；用用户提问的语言作答。
  • 提交方式是：以不带任何工具调用的纯文本结束这一轮。一个专门的观察器会把这段文本收下作为最终答案，前提是“收尾关卡”（finalize_gate，检查看板上是否还有未完成任务）放行。

合并之后还有一道代码修正

协调者提交后，一段网址修复代码（repair_citation_urls）会拿答案里的网址去比对所有证据卡里的网址白名单：模型常做的改写（换域名前缀、补后缀等）会在归一化后被识别出来，改回工具实际返回的写法；对应不到唯一网址的，记为“有歧义”。这一步完全由代码完成。

§ 06写报告的原理

验证：交之前，先让独立的人审一遍

报告在提交之前要经过一个独立的审查者。它有自己的上下文，看不到协调者是怎么想的，只拿到原始问题和草稿全文。它的名字是保留的：子智能体的名字里只要带 verifier（审查员）字样，系统就会强制换上内置的审查提示词，协调者为它写的系统提示词会被直接丢掉，协调者没有办法把审查者“教”得宽松一些。

终审员的五个阶段

  1. 完整性：仔细读原题，把每个子问题、子部分和要求明确列出来，逐条检查草稿是否回答，标出“已回答”或“缺失”。文件任务要读声明过的输出目录清单（可以读，不能写）；要检查发布前的候选文件，就按那个智能体报告里的路径去工作目录读；不许自己发明别的根目录，也绝不创建验证或确认文件。
  2. 正确性，用对的方法独立复核：不能只信草稿，也不能只是重读草稿的来源。推导 / 数学 / 逻辑类结论要从头重新推导和证明，用代码暴力验证小规模情形、符号检验公式、寻找反例，不成立的证明判失败，不管草稿说得多自信；事实 / 数据类结论要换一套不同的查询去搜、查一手来源，并用代码重算其中的数字。同时报告支持和反对的证据。
  3. 精度：具体数字、公式、名称是否是精确值，而不是近似值或另一个语境里的值？存在多个相似值（不同阶段、版本、情形）时，用的是不是对的那一个？
  4. 纪律：检查草稿是否遵守逐字合并：原子是否与证据完全一致（没有取整、归一化、改写、翻译、改名）；有没有任何证据都不支持的断言；冲突是否按最强证据取舍而不是取平均；是否严格遵守了规定的答案格式。
  5. 交付物：如果任务要求产出文件、表格、幻灯片、表格文件或代码，要检查交付物本身，而不是草稿里对它的描述：是否在指定位置、格式是否正确、是否包含所有要求的章节 / 字段 / 列 / 图、内容是否与验证过的答案一致。缺失、为空、格式错误、放错位置或不完整，即使文字答案正确也判“不通过”。纯文字任务跳过这一阶段。

它的输出也是固定格式：逐条列出每个子问题“已回答 / 缺失”“通过 / 不通过”及证据，再列精度问题、纪律问题、交付物检查结果，然后是发现的错误、得分（通过数 / 子问题总数）、结论（通过 / 需要修正 / 不完整）、缺失部分和修改建议。

仲裁员：只管一处冲突

  • 适用于多个智能体查同一个子任务却得出不同结论的情况。协调者用一个“附上某智能体报告”的标记（<attach agent="..."/>）把双方报告全文附进任务。
  • 它要找出分歧点和原因，并用对的方法仲裁，而不是站在更自信的那一方：推导或计算冲突就自己重算，让数学说话；事实冲突就打开双方引用的网址，必要时独立搜索。
  • 如果双方都站不住，就自己做一次简短调查来定论。输出范围、智能体 A 的说法、智能体 B 的说法、裁定结果和置信度。
  • 提示词明确禁止协调者“凭自己的记忆”解决冲突。

名字决定身份

名字 / 角色描述拿到的系统提示词
名字含 local_verifier，或角色描述里提到 conflict（冲突）仲裁员提示词
名字含 verifier（如 final_verifier、data_verifier、source_verifier）终审员提示词；协调者写的系统提示词被忽略
其他任何名字研究员提示词，末尾追加协调者写的“你的角色”一段

所以不要给想做研究的智能体起带 verifier 的名字。研究型智能体的角色描述被放在系统提示词的最后，这样前面不变的部分对所有同级智能体都一样，可以共用模型服务端的缓存（KV 缓存前缀），省时省钱。

§ 07写报告的原理

最高强度：做一个不肯轻信的协调者

配置档里的“团队强度”（team_effort）控制编排力度（派多少智能体、跑多少步），它和模型自身的推理强度参数是两回事。评测档和终端档都设成了最高强度。最高强度会在协调者的系统提示词末尾注入一段策略，把“多采样、按不确定性分配算力、交叉印证、对抗式证伪、验证后收尾”压进单次运行里。

译文你正以最高强度运行。目标不是快，而是收敛到一个经过验证的答案。……做一个毫不松懈的怀疑者。You are running at MAXIMUM effort. Speed is not the goal — converging on a verified answer is. … be a relentless skeptic.译自源码提示词 · workflows/agent_team/prompts.py
  1. 为独立性而分散，不为数量：每个非平凡子问题派 2–3 个智能体，它们至少在一个“独立性轴”上不同：不同的工作假设或拆法、不同的方法（从来源检索，还是推导计算）、不同的来源类别、不同的查询框架。检验很简单：如果两个智能体会跑同样的搜索，就没有分散。要在每个智能体的任务里写明它的不同角度。
  2. 把投入放到证据最弱的地方：读每份报告的“置信度”“未解决”“反面证据”三栏，把下一波智能体派到低置信、未解决或有争议的子问题上；已经印证的不再花钱；绝不平均分配。
  3. 先印证再相信：任何关键事实都不能只凭一个智能体定论，需要 ≥2 个独立智能体收敛；有冲突就派仲裁员，附上双方报告，让它从来源仲裁，绝不凭记忆。
  4. 主动找错，力度与证据薄弱程度成正比：把每个结论先当成错的，直到证据迫使你接受。支撑越薄（单一来源、推断而非检索、低置信、措辞含糊、有反面证据）就越要用力攻击：专门派智能体去证伪、找第二个独立来源、找反例。这既适用于中间结论，也适用于当前领先的最终答案（专门派一个智能体只为推翻它）。听起来自信但来源单薄的结论最危险。
  5. 验证之后才收尾：结束前派终审员，用不同的查询重新推出答案，并核对每个原子（数字、日期、名称、公式）；确认后才结束，发现缺陷就修复该子问题并重新验证。“跑几轮就交”是要避免的失败模式。

策略里还写着按难度校准：简单子问题一对印证即可，困难或有争议的值得多轮；拿不准要不要再分散时，就再分散。这段强度标签永远放在系统提示词的最后一行，位置固定不变，方便以后把它挪进模型的对话模板（chat template）。

§ 08写报告的原理

报告员：两次调用，只加引用

开源版只带一种报告员实现，即“快速报告员”。它由两次大模型调用和几道代码关卡组成。第一次调用只负责“挑来源”，而且只能按编号挑；第二次调用只负责“往草稿里插 [N]”。编号、参考文献列表、重编号全部由代码生成。任何一步出错，都退回协调者的原稿。

节点外层：时间与退路

  • 报告员的总时长预算（reporter_wall_time_s）默认 1800 秒，终端档为 900 秒，实际还要再按任务剩余时间截断：平台总时限很短时，协调者预留的时间未必还在，截断后能保证报告员以“保留原稿”的方式失败，而不是在写到一半时被取消。
  • 整个报告员外面包着一层超时控制；任何异常都只记日志、返回空更新，协调者的答案原样保留。成功时只替换答案字段（并把答案来源标记为“报告员”），证据状态不动。
  • 报告员用哪个模型，按这个顺序确定：显式指定的报告配置档（参数或环境变量）→ 内联配置档里的“报告模型”设置（report_llm）→ 当前运行配置档里的报告模型设置 → 自带评测档的设置。评测档的报告模型温度为 0、单次超时 600 秒；没有配置时，单次调用默认超时 200 秒。
  • 草稿为空时直接跳过。

候选准备（代码）

  • 准入：卡片必须有网址和非空摘要。摘要优先取卡片里的第一条来源原话（supporting_quotes[0]），其次才是卡片记录的断言，因为后面要拿断言去和摘要比对，原话更接近网址实际写的内容。
  • 去重：同一个网址只留一张卡，留摘要更长的那张（评审只看得到摘要文本，所以按“信息量”而不是先来后到决胜），幸存者保持首次出现的顺序。
  • 预算：按证据到达顺序累加，估算 token（词元，模型计量文本长度的单位；这里按字符数 ÷ 3 估算），超过 80,000 就截断，给评审调用的回答留出空间。不做打分。

大模型 ①：评审来源

  • 对每个保留的候选输出三样东西：编号（列表里的序号，绝不输出网址，系统手里已经有了）、标题（真实页面标题就照抄；只有标题是光秃秃的域名或网址片段时才重拟，少于 120 字符，不以句号结尾）、质量（高 / 中 / 低）。
  • 取舍原则：先看相关性，与问题和草稿里任何事实断言都不沾边的来源，不管档次多高都不给位置；再看可信度，宁可表小而硬，不要被弱来源填满。上限是天花板，不是配额。“低”档来源只有在没有更强来源覆盖同一断言时才保留，而且不能挤掉更强的来源。
  • 只返回一个 JSON 对象（形如 {"nodes": [...]}）。解析时只截取第一个 { 到最后一个 }，逐项校验编号不重复且在范围内；失败原因分成四类：回复无法解析、列表为空、没有有效编号、模型调用出错。任何一类失败都降级为“按到达顺序取前若干条”。
  • 代码据此建立引用白名单：先按质量排序再截断，默认上限 30 条（可通过运行参数或环境变量修改，范围 1–500，非法值回退默认）；并把真实页面标题回填。白名单为空就直接报错（“没有可采纳的证据”）走退路，因为没有可引用的来源时，重写只会比原稿更差。

大模型 ②：挂引用

系统提示词由三部分拼成：挂引用的主提示词、引用密度补充规则、确定性引用合约。用户提示词依次是原始问题、编号参考列表（标题 / 网址 / 摘要 / 来源类型）、协调者草稿、任务说明。

规则具体内容
忠实度（压倒一切）逐字照抄草稿：同样的句子、措辞、顺序、标题、表格、数字、详略。唯一允许的改动是插入 / 删除 / 改指 [N]，以及修复坏掉的 Markdown 表格。不改任何数字、单位、日期、名称或基线，片段和草稿矛盾时草稿优先，只是不引用它。不删任何句子、行、要点、表格、章节，删掉方法表、推导或被否决方案的讨论是最严重的失败。不新增任何断言。不重算：改了一个输入而结论不变，会产出自相矛盾的报告。不调整章节顺序、标题，不合并也不拆分

代码收尾

  • 格式清理（clean_report_v3）：清掉多余格式，但能识别代码块，不动代码块里的内容。
  • 语言判断：语言设置为“自动”时，从草稿检测语言；不这么做的话，中文报告会被加上英文的“References”标题。
  • 参考文献定稿（finalize_report_with_canonical_references）：删掉模型自己写的参考文献，按首次出现顺序给 [N] 重编号，追加规范的参考文献块。正文没有任何 [N] 时原样返回，不硬加列表。
  • 这一步用的是全文字符串替换，不认识代码块，所以外面包了一层“代码保护”：源码注释里记录，在真实回放中，代码里的 data[1, 2] 曾被当成引用拆开重编号。
  • 交付物检查：原稿里有输出文件路径或代码块，而改写后某一类全部消失，就报“交付物丢失”错误，退回原稿。“引用再多也弥补不了丢掉用户要的交付物。”
  • 记录指标：候选数、实际给到写作调用的参考数、评审是否降级及原因、语言；报告员的原始输出也写进运行轨迹，方便和最终版本逐行对比。

来源可信度：宁可不引，也不弱引

报告员的提示词里有一句很坦白的话（译自英文）：“用裁判模型做的评测发现，报告输在来源可信度上，而不是引用数量上。”于是它定义了一套全链路唯一的五档排序，并配上一条硬禁令。

  • 硬禁令：价格、官方规格、财务数据绝不能由第 4 或第 5 档来源支撑。这两档只能支撑用户体验、社区情绪、观点这类主观内容，并且句子要写成“有用户反映……”，而不是“价格是……”。
  • 宁缺勿滥：没有第 1–3 档来源写到这件事，就不引用。一个弱引用比没有引用更糟：[N] 读起来就是“已核实”，论坛或预测站的引用会制造出这件事并不具备的可信度，是一层“引用外衣”。
  • 不追求引用数量：更少、更硬的引用胜过更多、混杂的引用；不要为了避免“没有引用”去找第 4、5 档来源。
  • 规则 J · 主体要对得上：当句子说“X 需要 Y”或“机构 Z 做了 W”时，所引来源必须以 X / Z 为自己的主语，仅仅提到 X 或 Z 不算。如果证明 Y 的来源其实绑定的是另一个主体，就把它引在那个主体自己的句子下，或者这句不引。同一主体用同一来源；挂之前先确认 [N] 实际讲的是什么，不要默认最显眼的候选就是对的。
  • 没有“只有这一个来源”的例外：本地话题有时只有第 4、5 档来源沾边。主观说法可以引，但要标明是主观的；价格、规格、财务数据无论来源多少，都按宁缺勿滥处理。
  • 同一断言有更高档的来源写到时，优先引用更高档的。这只是在来源之间做选择，绝不意味着可以改草稿的文字。

§ 10写报告的原理

所以报告为什么好

把前面九节压成一张表：报告质量拆成五个维度，每个维度都有两到四个机制在保证，而且这些机制分布在链路的不同位置，互相补位。大模型在其中的角色被限定得很窄，自由发挥的空间很小。

  1. 拆题带来完整：先想后拆，每个子问题登记在看板上，后面的草稿和复核都对照这份清单。
  2. 结构化报告带来可用的原材料：精确原子、逐字网址、明确的不确定性，协调者合并时不需要猜。
  3. 逐字合并保住细节：不取整、不改写、不平均，长度不小于最详细的报告。
  4. 多来源印证 + 对抗式验证保证准确：本质是用更多推理算力换准确率（推理时扩展，test-time scaling），在单次运行里做了“多采样 + 投票 + 证伪”。
  5. 可信度分档 + 宁缺勿滥让引用靠谱：来源只能按编号选，弱来源不许支撑硬数据。
  6. 确定性后处理 + 失败保留原稿守住下限：加引用这一步只可能让报告变好，不会让它变差。

需要带着的几点保留

  • “好”是按评测标准调出来的。提示词直接写了裁判模型评测时发现的扣分点，很多规则明显是冲着大模型打分的偏好去的。“至少和最详细的报告一样详细”会让报告偏长，不一定适合所有读者。
  • 开源版不是完整版：更重的“重型”写作后端没有开源，开源版只有“草稿 + 挂引用”的快速实现。
  • 成本高：最高强度下每个难题派 2–3 个智能体，再加上印证、证伪和验证，token 和耗时成倍增加。
  • 终端界面默认不开报告员：交互模式下看到的就是协调者的逐字合并稿，正文里的引用由协调者按第 4 步第 7 条自己标注。

第 II 部分

用什么模型，出了问题怎么兜底

问它用的是什么模型？怎么做兜底：比如模型幻觉出了错误的数字、重复输出同一个字直到撞上输出长度上限（maxToken）、输出的 JSON 不合规，这些问题怎么处理？

这一部分讲“模型不靠谱时怎么办”。大模型会编数字、会陷进重复、会写坏格式，接口也会出故障；系统稳不稳，取决于这些意外有没有被接住。先看模型与采样参数，再逐类看四种失败：数字幻觉、重复与截断、格式错乱、接口故障。每一类都标明哪些由代码处理、哪些只能靠流程。

为什么智能体循环的温度不能是 0

直觉上评测应该用温度 0 来减少随机性，但评测档配置文件的注释给出了三组实测，说明这在这个模型上会把“偶尔发散”换成“确定性死锁”：

  1. 一个已经陷入“推理失控”的上下文，在自部署端点上以温度 0 重采样 4 次，4 次输出逐字节相同，没有任何概率离开这个吸收态。有一道题累积了 117 次失控，烧掉 176 分钟，最后以“没有调用工具”的状态退出。
  2. 官方端点会忽略温度（发 5 次温度 0 的请求，得到 5 个不同结果），所以能逃出来。同样 19 道题上，失控次数从 516 降到 37，“没调用工具就退出”从 9/9 降到 0/9，正确数从 0/9 升到 5/9。
  3. 必须真正离开 0，只调 top_p / top_k 没用：温度为 0 时，SGLang 直接取概率最高的那个词（argmax），完全不做随机采样，这两个参数根本不起作用。

温度 1.0、top_p 0.95、top_k 20 这三个值取自模型自带的生成配置文件；代价是单次运行的结果波动更大，靠多跑几次（命令行参数 --runs N）取平均来消化。报告员则刻意保留温度 0：它只是一次不带工具的合成调用，没有循环可以卡住，确定性比“逃逸概率”更有价值。

§ 13模型与兜底

防“车轱辘话”：重复输出直到撞上长度上限怎么办

模型卡在重复或无休止的推理里，是长任务最常见的失败之一。FrontierAgent 在三个时间尺度上拦截它：一次输出进行到一半时、一次调用结束时、跨越多轮时。最外面还有一圈时间上限。

① 流式输出中

  • 重复片段检测：默认参数是片段长度 30–500 字符、至少重复 6 次、输出满 800 字符才开始检查、每 200 字符检查一次。也就是说，输出累计 800 字符后，每新增 200 字符扫描一次末尾，发现长 30–500 字符的片段连续重复 ≥6 次，就中断这次流式输出。注释解释了取值：片段短于 10 个字符，误报率会爆炸；次数低于 6，会误伤“1) X 2) X 3) X”这类正常的枚举；高于 6 则白白浪费 token。它以“代理”的方式包在模型调用外面，还得挂一个空的观察器，逼循环走流式请求，否则收不到逐块输出。默认不开启。
  • 只推理、不出正文的看门狗：两个阈值，推理时长 120 秒、推理量 16,384 token，只要有一个达到就中断。设置其中任一项都会让循环改走流式请求，因为只有流式才看得到推理正在进行。Anthropic、OpenAI Responses、Bedrock 这几种协议从不走流式，会忽略这两项。注释建议调参时以 token 上限为准：同样的时长能生成多少 token，会随服务端并发升高而缩水。

② 单次调用结束时

  • 推理失控：一次调用成功返回，但正文为空、没有工具调用，而且结束原因是“长度到顶”，或者输出 token 多到不可能是正常的空回复（有些网关会把结束原因弄丢），就判定为失控。第一次失控后，重试会把单次输出上限降下来（最多 8192，并根据实际观测的用量推算，不会把低上限的配置反而调高），同时附一句临时提醒：“上一次把预算都花在私下推理上了，这次请简短推理，尽快给出正文或工具调用。”
  • 提醒以“用户”身份而不是“系统”身份发送：不同服务商对插在中间的系统消息处理不一致，Anthropic 适配器只提取开头的系统消息，很多推理模型的对话模板也只渲染第一个系统消息块。这句提醒不进入长期保存的对话历史。
  • 默认最多重试 2 次（可用环境变量修改）。注释记录：在某类逻辑谜题任务上，降低上限后重新采样从来没救回来过，所以那些部署设成 1 次，每次失控能省 150–400 秒。重试用完后把响应原样返回，交给循环里“你没有调用工具”的提示来兜底；第 1 轮之后的失控绝不升级成致命错误。
  • 有正文但被截断：这是唯一能确定“模型还没说完”的情况，必须和“模型主动不说了”区分开，两者都表现为“没有工具调用”。截断的正文已经进入历史，循环追加一句“从断点继续”，默认最多 2 次，而且有自己独立的次数预算，不占用“没调用工具”提示的次数。如果每次续写都还被截断，就标记为“输出被截断”后结束，不会被伪装成一次正常的“没调用工具”结束。

③ 跨轮次

守卫检测什么怎么处理
重复调用守卫连续几轮的工具调用一模一样（反复读同一个死链接、反复跑同一条命令、反复读同一个文件）3 轮提示；在子智能体上第 6 轮强制停止。协调者身上刻意不挂，因为协调者等子智能体时，本来就要反复用相同参数调用“收报告”
重复文字守卫连续几轮的可见文字几乎一样（按相邻词对的重合度计算）子智能体上会停止；协调者上只提示，因为协调者停了整个任务就停了
重复搜索撤销本轮要做的网页搜索，在这个循环里已经执行过且返回过内容在搜索执行前撤销这一轮并重新采样，不占用轮数上限；带有“结束”类工具的那一轮绝不撤销
卡死目标守卫按域名统计失败，而不是按完整的调用文本先提示，再屏蔽该域名；一次成功会清掉它的失败记录
无进展守卫协调者连续多轮只调用管理类工具（建智能体、派任务、收报告、停智能体），期间还在反复新建智能体6 轮提示，12 轮以“空转无进展”为由停止（详见第 19 节）

注释解释了为什么重复调用守卫必须能“停”：重复搜索的撤销次数用完后，后续重复会被永久放行，而一个在温度 0.7 下都能逐字复现同一次工具调用的模型，永远等不来“新请求”；重复文字守卫需要约 60 个字符的相似可见文字才能触发，但用 <think> 标签输出推理的模型在打转时，内容全在思考区里，可见文字什么都没有。所以对于“只在工具调用里打转”的循环，重复调用守卫是唯一能把它结束掉的守卫。

时间上限

  • 一次“逻辑调用”的总时长上限 900 秒，包括排队、每一次实际发出的请求，以及重试之间的等待。
  • 整个任务有研究截止时间，截止时间观察器在用掉 75% 时发出预警。
  • 收尾预留观察器在协调者还剩 8 轮时注入一次性的收尾指令；“最后一轮”机制在倒数第二轮提醒，最后一轮拿走所有工具、只能输出纯文本，这时即使结束检查没通过也接受答案，而不是让答案随着轮数耗尽一起丢掉。
  • 温度本身也是一道防线：见上一节，温度 0 会让失控变成无法逃出的死锁。

防格式错乱：JSON 与工具调用不合规怎么办

处理这类问题的思路分两层：能从结构上避免的就不让模型手写 JSON；避免不了的，就准备好多种解析方式依次尝试，解析失败要么修复、要么重试、要么降级，而不是让整个任务崩掉。

从结构上避免

  • 优先用原生工具调用（function calling）：由推理服务的解析器（如 SGLang 的 qwen3_coder）把工具调用变成结构化字段，模型基本不需要手写 JSON。
  • 最终答案是纯文本，不是 JSON：协调者以不带工具调用的纯文本结束。
  • 需要模型做选择的地方只让它输出编号：报告员评审只输出候选的序号，网址由系统填回。

解析级联：五种格式依次尝试

  1. 原生工具调用：把服务端给出的结构化调用整理成执行器需要的统一格式（工具名、参数、编号）。
  2. <tool_call>{JSON}</tool_call>：模型把调用写进正文时，从标签里解析 JSON。
  3. 被截断的 <tool_call>{…：闭合标签或最后的大括号因为撞上输出上限而丢失，用括号配对算法找到对象结束的位置，恢复出单个调用。
  4. Qwen 风格 XML：<tool_call><function=名><parameter=参数>…。
  5. Seed 风格 XML 与推理模式下的 <|FunctionCallBegin|>[…]<|FunctionCallEnd|> 包装（上游代理没把它重新打包成原生调用时出现）。

在任何解析器看到文本之前，混进正文的 <think> / <thinking> / <reasoning> / <seed:think> 等标签会先被剥掉；只有开标签没有闭标签的，从开标签处截断。剥下来的推理内容会附到响应元数据里，不会丢。MCP 工具（通过外部工具接入协议挂进来的工具）在原生调用不可用时，也有 <use_mcp_tool> 这种文本回退写法。

解析之后的检查

  • 参数丢失：Qwen / SGLang 上观察到，生成在参数闭合标记之前停止时，会得到一个空壳调用（参数为空值或空字符串），或者一个合法但缺了必填字段的对象（常见的是 {}）。解析失败的片段在规范化时也会退化成 {}，到工具校验时已无法区分。执行前的代码按每个工具的必填字段检查，发现丢失就重放这次请求（剩余时间太少时跳过）。
  • 类型不对：有些模型把列表或对象写成 JSON 字符串传进来，一段类型纠正代码会自动转回。
  • 只用文字描述调用（“我现在调用 run_python_code(...)”）：“泄漏调用重试”观察器一旦在文本里发现允许使用的工具名或 XML 包装，就注入提示“请通过正式的工具调用接口调用，不要用文字描述”，并按 0.3 → 0.6 → 1.0 逐级提高温度重试；每个任务有总次数上限，防止模型无视提示时陷入死循环。

业务层 JSON：报告员评审

评审结果的解析函数从不抛出异常：只截取第一个 { 到最后一个 } 之间的内容解析；JSON 错误、类型错误（例如模型返回了字符串数组而不是对象数组）都被捕获；逐项校验编号唯一且在候选范围内，无效项丢弃。整体失败时返回失败原因，降级为按到达顺序截取。报告员整体失败时，保留协调者原稿。

七条派发约束

可选：先规划，再执行

配置档里的“规划模式”打开后，协调者的工作被切成两段。规划阶段它是“规划者”，只能读和登记，任何派活、写文件、提交答案都会被代码拦下；调用“结束规划”工具后才解锁团队。还可以选择让执行阶段从一张干净的上下文开始，只继承看板。

规划阶段的规则

  1. 只读，几乎不搜索：只能用本地文件搜索工具查看输入文件，外加“添加任务”“更新任务”。调用“结束规划”之前，其他一切都被拦截。网页搜索只是一个罕见的逃生口，仅当题目里的术语确实陌生、不知道意思就没法规划时使用，最多一次概念查询，绝不用来收集证据或求解。
  2. 把问题拆开，每个子问题用“添加任务”登记，再调用“结束规划”。推荐的形状是：候选发现 → 属性提取 → 约束匹配 → 验证 → 最终提取。每个任务要写明具体的实体、来源或数值，不能只是把题目重复一遍。
  3. 规划有预算：几十轮之内要结束；否则到了规划轮数上限（40 轮）会被自动结束，带着当时的看板进入执行。
  4. 规划阶段不许回答问题、选选项、算最终值，也不许写任何“分析 / 总结 / 结论”。
  5. 规划中碰巧发现的答案不是答案：不许提交（被拦截），也不许当成定论去自我验证，而是加一个任务，让子智能体在执行阶段独立地重新推导和验证。“每个答案都必须由团队挣来，而不是由你。”

执行阶段

  • 开启干净上下文时，执行循环的系统提示词以“执行模式”开头：规划已经完成，看板在用户消息里；你的工作是运行团队，每个看板项都要创建子智能体并派出去，自己不许回答。
  • 收报告、交叉印证，结束前派终审员独立重推答案；“不许单干”和“必须验证”两道结束检查仍然生效。
  • 研究者和验证者只在工作目录写候选文件；答案验证后只派一个带固定输出路径清单的整合者；协调者自己不写也不移动文件。
  • 规划模式一旦开启，“规划已启用”这个标记在结束规划之后仍然为真，所以结束检查会一直按规划模式执行。

默认没开

自带的基线档、评测档、终端档都没有打开规划模式（planning_mode: false）。这意味着规划模式的这些硬拦截，以及第 20 节里依赖它的两道结束检查，在默认配置下都不生效。

运行中把它拉回来

限制和约束解决不了所有问题，协调者在运行中仍然可能空转、跑偏、忘了收尾。FrontierAgent 在它的每一轮结束时挂了一圈观察器（observer），有的只提醒，有的会强制停止；报告本身的格式也在不断把它的注意力拉向薄弱处。

报告格式本身就在纠偏

  • 子报告强制包含“置信度”“未解决”“反面证据”“冲突”四栏，协调者收到的不只是结论，还有“哪里没把握”。最高强度策略直接要求往这些地方追加人手，并专门派智能体推翻当前的最佳答案。
  • 报告的完成状态由代码标注：每份报告带一个状态：完成（给出了最终答案）、未完成（轮数或预算用完、提前停止、被截断）、失败（被取消或崩溃）。每批回流的末尾有一行状态汇总，写明还有哪些在运行、哪些暂停、是否已全部收齐，并标出这批里有几份不完整。提示词要求把不完整或失败的报告当成部分证据：用有针对性的追问补上缺口，或在综合时说明不确定性。
  • 报告回流有两种方式：子智能体在协调者这一轮运行期间跑完，它的报告会在下一轮之前自动注入（自动收齐观察器）；下一轮开始时仍在运行的，要调用“收报告”并设 1800 秒超时，原地等待。短于 300 秒的超时等于只是看一眼，难题通常要 3–10 分钟，所以默认用 1800 秒。
  • 冲突必须交给仲裁员，提示词明确禁止协调者凭记忆裁决。

无进展守卫的精确判定

结束前的把关，以及它管不住的地方

最后一道关是提交之前：看板没清空不许结束，独立的终审员从原题重新列出子问题，相当于对协调者拆题做一次审计。但要看清楚：这些约束里有多少是代码强制的，有多少只是写在提示词里的要求。

出口的三道关

  • 看板没清空，不许结束（收尾关卡）：还有待办或进行中的任务时，协调者提交的答案会被打回，提示它对每一项调用“更新任务”，标为“已解决”（已回答且已印证）或“已取消”。这一条由代码强制，始终生效。建了但从没派过活的智能体只记警告，不阻塞。
  • 终审员是对协调者的独立审计：第一步是从原问题自己重新列出所有子问题，再逐条对照草稿，协调者拆题时漏掉的部分在这里能被发现；事实类换一套查询重新检索，推导类从头重算；它在独立的上下文里工作，看不到协调者的推理，不会被带偏。
  • 报告员只加引用：网址被纠正回工具实际返回的写法，编号之外的来源无法引用。

规划模式开启时，收尾关卡还多两道检查：没有任何子智能体实际做过任务就拒绝（“这是单干，规划模式禁止”）；做过任务的智能体里没有名字带 verif 字样的就拒绝（“答案还没被独立验证”）。另外，最后一轮工具被去掉之后，即使检查不通过也会接受纯文本答案，避免答案随着轮数耗尽一起丢失。

它仍然管不住的三件事

  1. 合并时抄错或编造：没有代码去比对协调者的草稿和子报告原文，只能依靠逐字合并的提示词和最后的审查员。
  2. 拆题方向从一开始就错：审查员能发现“漏了子问题”，但如果题目本身有歧义、协调者选了错误的理解，审查员也可能沿着同一种理解去查。
  3. 归根到底仍依赖模型本身：官方搭配的是面向智能体场景的 Apodex-1.1。这些机制能减少跑偏的次数、限制跑偏的程度，但协调者本身太弱时，机制救不回来。

长链任务为什么不崩

问一个写报告的长任务有很多小环节，任何一个出错都可能导致失败或质量下降。100 个节点、每个 90% 的稳定性，乘下来整体就非常低了，这个项目是怎么解决的？

这一部分回答“步骤那么多，为什么不会一路错下去”。直觉上，环节越多，出错的机会越多；但这个直觉背后藏着几条假设，只要把它们一条条拆掉，长链任务就能稳住。下面从 0.9 的 100 次方这个算式的四个前提出发，逐条看它是怎么被打破的：可检测的重试、降级而不中断、并行冗余、闭环纠偏、少让大模型决定。

§ 21长链任务为什么不崩

0.9 的 100 次方：先看清这个算式的前提

长任务由很多小环节组成，每个环节成功率 90% 的话，100 个环节乘下来只剩约 0.003%。这个算式没有错，但它默认了四个前提。FrontierAgent 的可靠性设计，可以理解为逐条打破这四个前提。

算式成立的四个前提

  1. 100 个环节是串联的：任何一个都必须成功。
  2. 每个环节只跑一次：没有重试。
  3. 任何一个环节出错，整个任务就失败：没有退路。
  4. 错误没人发现，会一路传到最后。

接下来五节对应五种打破方式：让失败能被发现从而有效重试（第 22 节）；出错时降级而不是中断（第 23 节）；用并行冗余代替串联（第 24 节）；用闭环纠偏阻止错误传播（第 25 节）；以及减少需要大模型决定的环节、把状态放在模型之外（第 26 节）。

§ 22长链任务为什么不崩

打破“只跑一次”：让失败能被发现，重试时换条件

如果失败能被代码判断出来，重试 k 次后单步成功率就从 p 变成 1 − (1 − p)ᵏ：90% 的环节重试 2 次是 99.9%，这时 100 个环节连乘还有约 90%。关键在“能被代码判断出来”，以及“每次重试都要改变点什么”。

§ 23长链任务为什么不崩

打破“一处出错就全失败”：降级，而不是中断

这是最核心的一条。环节被分成两类：质量类环节出错就降级，退回上一个已有的可用结果，任务照样完成，只是质量差一些；安全类环节出错就直接停止，绝不绕过。这样失败从“全有或全无”变成了“这次质量打了几折”。

四级退路

  1. 干净上下文重答：把历史重新组装成一条干净的用户消息，做一次不带工具的大模型调用让模型给出答案。重建干净消息是为了避免原历史里的畸形工具调用让这次请求以同样的方式失败。这次调用也走带预算的备用链。
  2. 用已有草稿：上一步失败，或只返回了混进来的标记，就用协调者自己已经写出的可见草稿（同样剥掉推理和工具调用）。在这里草稿排在子报告前面，因为它已经是一次综合，下游没有人会再把原始报告合成一遍。
  3. 拼接子报告：连草稿都没有，就把已收到的子报告拼起来。
  4. 最小答复：最后输出一段明确说明“只完成了一部分”的答复，而不是把原始的工具调用 XML 当答案。

每次走了退路，都会在元数据里记下“答案是抢救出来的”以及走的是哪一级，事后能统计各级退路被触发了多少次。交给报告员的场景则相反：报告员还在后面，原始子报告对它是更好的输入，所以那条路径上的排序是反过来的。

§ 24长链任务为什么不崩

打破“串联”：用并行冗余代替串行步骤

同一个子问题派 2–3 个智能体去查，只要有一个查对就够。两个 90% 的智能体同时出错的概率是 1%，三个是 0.1%。但这有一个前提：它们必须是独立的。

  • 冗余必须是独立的：三个智能体用同样的搜索词、看同样的网页，就会一起错。最高强度策略写明，派出去的智能体必须在假设、方法、来源类型或查询角度上至少有一处不同，并且要在任务里写清楚区别；检验标准是“如果两个智能体会跑同样的搜索，就没有分散”。“至少两份独立报告互相印证”也是同一个道理。
  • 真正必须串行经过的环节很少：拆题 → 并行研究 → 合并 → 验证 → 加引用，串行的只有这几步。中间那部分虽然调用了几百次大模型，但它们是并行、冗余的，不是一条链上的 100 个环节。
  • 并行还能省时间：同一次派任务里的多个任务并行执行，并发数由资源管控控制，超出上限的排队等待而不是被拒绝。

§ 25长链任务为什么不崩

打破“错误一路传到最后”：用闭环代替开环

这是它和固定流程编排差别最大的地方。开环流水线里，每个节点把输出交给下一个，下一个只管接着做，上游的错误会被当作正确输入一路放大。闭环的智能体循环里，每一步都先看到上一步的结果再决定下一步，错误有机会在发生后被看到、被纠正。

  • 工具出错，错误信息会作为观察结果交还给模型，模型可以换个做法：网页读不出就换网址，某个域名反复失败就被屏蔽。
  • 子报告写“这一点没查到”（“未解决”栏），协调者可以针对性地追加任务；报告被标为“未完成”，就被当作部分证据并安排补查。
  • 两份报告冲突，交给仲裁员回到来源仲裁。
  • 审查员找出问题，流程可以回到第 1 步重新调查（第 6 步的规定）。
  • 再加上空转检测、重复检测、失败域名屏蔽这些看守，专门拦截“越走越远”的失败方式。

概率上的含义

在闭环里，出错不等于失败，只有“出错之后没被发现、也没被纠正”才等于失败。单步的“有效失败率”因此远低于它的原始出错率。

§ 26长链任务为什么不崩

少让模型决定，把状态放在模型之外

最可靠的环节，是根本不让模型做决定的环节；最不怕丢的状态，是不存在模型上下文里的状态。FrontierAgent 在这两件事上都下了功夫，而且这些设计大多来自对真实运行记录的逐个排查。

能交给代码的就不交给大模型

  • 让某些错误在结构上不可能发生：模型只输出编号而不输出网址，所以编不出链接；引用编号、去重、参考文献列表全部由代码生成；写输出目录的权限由结构化字段授予，提示词里怎么写都不管用。
  • 缩小每一步大模型调用的职责：报告员只负责加引用，评审只负责挑编号。任务越窄越容易做对，也越容易检查。
  • 每少一个大模型自由决定的环节，链条上就少一个 0.9。

状态存在模型之外

  • 任务看板和证据卡保存在元数据里，不依赖某一轮的输出；哪一轮输出坏了，已经积累的东西都还在。
  • 被截断的工具结果可以找回：工具结果在交给模型之前会被截短（子智能体为 15,000 字符，命令行为 4,000 字符），只留一个“已截断”标记，但完整结果写在轨迹文件里，模型可以用“找回结果”工具（recover_result）按轮次和调用编号把没看到的部分取回。
  • 上下文快满时自动分层压缩，而不是直接崩掉。
  • 会话有存档：每次运行的目录里有检查点（checkpoint）、运行轨迹（trace）、引擎日志和轨迹文件；带上 --resume 参数可以接着跑，终端里的 /revert 命令可以撤销本次会话的改动。

§ 27长链任务为什么不崩

一句话总结，以及代价

它解决链式失败的办法，不是把每个环节都做到接近 100%，而是让整体可靠性不再是每一步成功率的简单连乘。

  1. 失败能被发现，所以可以有效重试，而且每次重试都换条件。
  2. 失败了有退路，任务降级而不是中断；安全边界例外，出错即停。
  3. 用并行冗余代替串联，并要求冗余真正独立。
  4. 靠闭环纠偏，错误不会一路传下去。
  5. 能交给代码的就不交给模型，状态放在模型之外，减少出错的机会。

代价和局限

  • 用成本换可靠性：冗余派发、反复验证、重试，意味着 token 消耗和耗时成倍增加。
  • 单环节的保障不完全靠代码：数字对不对、必须经过审查员，在默认配置下只是提示词要求，代码并不强制；重复片段检测也默认关闭。
  • 最终结果远不到 100%：README 里智能体团队在各评测上的得分在 35.3 到 78.8 之间。这些机制解决的是任务能不能稳定跑完、结果能不能用，而不是保证每次都答对。

结语四个问题的答案

把四轮追问压成四句话

  1. 报告为什么好：没有自由发挥的写手。拆题保证完整，结构化子报告提供精确原料，逐字合并保住细节，多来源印证与对抗式验证保证准确，可信度分档与宁缺勿滥让引用可靠，确定性后处理与失败保留原稿守住下限。
  2. 模型与兜底：不绑定模型，官方搭配 Apodex-1.1，智能体循环温度 1.0、报告员温度 0。重复与截断有三层拦截加时间上限，格式错乱有五级解析级联与升温重试，接口故障按类型退避或换服务商；数字对不对没有代码校验，只靠流程和独立复核。
  3. 编排模型：不给它任何获取事实的工具；派发要自动附原问题、限任务数、限权限、过资源管控；运行中有观察器提醒或强停；结束前看板必须清空，并由看不到它推理的审查者从原题重列子问题。其中“必须验证”在默认配置下只是提示词要求。
  4. 长链可靠性：不把每一步做到 100%，而是让失败能被发现并换条件重试、出错降级不中断、用独立的并行冗余代替串联、用闭环阻止错误传播、能交给代码的就不交给模型。代价是成本，结果也远不到 100%。

术语

术语在本笔记里的意思
智能体（agent）由大模型驱动、能自己调用工具、一轮轮推进任务的程序
大模型（LLM）大语言模型，本笔记里指驱动智能体的那个模型
token（词元）模型计量文本长度的单位，和字数大致相当，具体换算因模型而异
智能体团队（Agent Team）FrontierAgent 的多智能体工作流：一个协调者加一群子智能体
协调者（coordinator）智能体团队的主智能体，负责拆题、派活、收报告、合并草稿，不直接获取事实
子智能体（sub-agent）被协调者创建和派活的智能体，负责检索、推导、计算、验证，最后用“提交报告”工具交报告
报告员 / 快速报告员（reporter / fast reporter）协调者之后可选的一步，只往草稿里加引用编号，不改正文
审查员 / 终审员 / 仲裁员（verifier / final_verifier / local_verifier）名字带 verifier 的子智能体统称审查员；终审员在提交前独立复核整份草稿，仲裁员只处理一处冲突
原子（atoms）报告里不可改动的最小事实单元：数字、单位、日期、公式、专有名词、引用
逐字合并（verbatim merge）协调者把子报告里最具体的内容原样复制进草稿的做法
观察器（observer）挂在智能体循环上、在每轮前后检查并可以提醒、撤销或停止循环的组件
配置档（profile）一份 YAML，决定模型、采样、轮数、工具、报告员、团队强度等
出错降级 / 出错即停（fail-open / fail-closed）出错时退回已有结果继续 / 出错时直接停止
推理失控（reasoning runaway）模型把单次输出上限全花在推理上，没有正文也没有工具调用
推理时扩展（test-time scaling）用更多推理时的算力（多采样、验证、搜索）换更高的准确率
扇出 / 扇入（fan-out / fan-in）把任务并行派给多个智能体 / 把它们的结果收回来
KV 缓存前缀多个请求共享的提示词开头部分，推理服务可以复用它的计算结果
